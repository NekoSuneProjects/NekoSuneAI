- [x] [NODE-CONVERSE-01] `/api/nodes/converse` (`nekosuneai/node_converse.py`): a paired node POSTs a captured transcript and gets back the assistant reply text, TTS audio to play locally, and any node commands the reply implies. Node-device-token only (never falls back to dashboard auth), rate limited per node (1s between turns, 20/minute, 800 chars), and returned commands are filtered through the same capability policy `enqueue()` enforces. Commands come back inline rather than queued so a spoken answer is not a poll cycle late; they are audited via the new `PeripheralNodeRegistry.record_event` since they bypass `enqueue()`. A play/stop request becomes `music.play`/`music.stop` for the *node* instead of `handle_media_request` playing on the backend host, which is what the owner means when they ask the Pi in their living room for music. Local backend TTS/media output is suppressed for the duration of a node turn so the backend host does not talk to an empty room. Consumed by Pi Proxy's wake word and dashboard push-to-talk (see `PiProxy/TODO.md`).
      **Not yet verified on a deployed container** — exercised against a stub backend and stub agent only.
- [x] [NODE-CONVERSE-01] Music routes to a paired Pi Proxy node instead of playing on the backend host (`nekosuneai/node_music.py`, `NodeMusicRouter`). `YouTubeMusicPlayer` resolves with yt-dlp and plays with ffplay *on whatever machine runs this backend*, which is wrong twice over for a VPS deployment: YouTube's bot/cookie verification blocks datacenter IPs ("confirm you're not a robot", age walls) where a home Pi's residential IP resolves fine, and the audio would come out of a sound card in a datacenter rather than the owner's room. When an online `pi-proxy` node advertising `music.play` exists, the same phrasings `handle_music_request` already understood become `music.*` node commands; with no such node the backend falls through to its own player, so a deployment without a Pi Proxy is unchanged. Shared by the dashboard/chat pipeline and by `node_converse`, so a spoken "skip this song" and a typed one mean the same thing — except that a node turn sends commands back to *that* node, so talking to the kitchen Pi does not start music in the living room. `music.status` is answered from heartbeat state rather than by queuing a command. Node auto-selection prefers the lowest `node_id` deterministically; `MUSIC_NODE_ID` pins one. A node that does not advertise a given control falls back to the backend rather than swallowing the request. Client side is `build/pi-proxy-release`'s `music.py`; see [docs/NODE_MUSIC.md](../docs/NODE_MUSIC.md).
      **Not yet verified on a deployed container** — exercised against stubs and an in-process end-to-end (router -> registry queue -> node dispatch).
- [x] [NODE-CONVERSE-01] A node turn returns what the assistant actually said. `_pipeline` is written for the desktop GUI: it pushes the real reply through `_push_chat` and *returns a UI status string* — "Ready.", "Hands-free listening.", "Media request handled.". `node_converse` used that return value, so a node asking "hello" was answered "Ready." and the LLM's reply (web search and all) never left the backend. The reply is now captured from the `_push_chat` call, which every path takes — webgui's own pipeline and webserver's routine/briefing/stream handlers alike — filtered to `role == "assistant"` so system notices ("Searching: …", the music announcer) are not mistaken for an answer. The swap is serialised with a lock, since it mutates the shared `Api`, and restored by deletion rather than reassignment so no instance attribute is left shadowing the class method (`_pipeline`, which webserver *does* override, takes the other branch).
- [x] [NODE-CONVERSE-01] Capability policy: `kind: "write"` still defaults to `confirm` and still refuses a self-declared `allow`, except a narrow per-node-type allowlist (`_NODE_TYPE_AUTO_ALLOW`) that lets a `pi-proxy` node register `audio.speak` and the `music.*` write controls (`play`/`stop`/`pause`/`resume`/`skip`/`volume`) as `allow`. Without this a freshly paired voice node could not speak its own reply or start the music it was just asked for — every one of those is a write, so its first command raised `PermissionError` and the node looked dead on arrival. `console.command` and `camera.snapshot` deliberately stay at `confirm`, an owner's later `deny`/`confirm` still wins, and other node types are unaffected.
